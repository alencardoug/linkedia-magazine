# Weekly Visual Laboratory

## A theme is a reusable software asset
Every experiment gets `themes/lab-YYYY-wWW/` (e.g. `themes/lab-2026-w43/`, theme id `lab-2026-w43`) with code, scoped styles, demo page, `README.md`, references/licenses, before/after screenshots (can remain in the private design archive if binaries), `theme.json`, accessibility notes, responsive behavior, performance notes, test references, portability instructions and source Git commit/tag. Public deployment ships only assets needed for active and previous theme, unless history pages require more.

## Theme contract (engine decision D-025)
- Every theme renders the same semantic, theme-agnostic markup; stable hooks are `data-*` attributes and CSS custom properties (design tokens).
- A theme = CSS scoped under `:root[data-theme="<id>"]` + an optional enhancement module, dynamically imported only when that theme is active and the device allows it (no reduced motion, WebGL available, etc.).
- Themes never change article content DOM, never fetch data and never block reading; any runtime error falls back to `minimal-dark`.
- `minimal-dark` is CSS-only and fully readable without JS.
- The stored choice is applied before first paint by a tiny inline script; without JS the build-time default applies.

## Immutable baseline and rotating slots
Permanent: `themes/minimal-dark` (dark, readable, unchanged except bug/security fixes). On week rollover, **previous** points to last week's current experiment, and **current** points to the new experiment. Once the first experiment exists the selector exposes exactly 3 controls and defaults to current (before that: no selector; with a single experiment the previous slot is shown disabled). The choice may persist in `localStorage` (wrapped in try/catch) with a safe default. All earlier themes remain in Git and can be reused in other projects.

## As built (1C-01)
- **Package.** `themes/<lab-id>/` holds `theme.css`, `README.md` and, only when the manifest entry declares `"enhancement": { "requires": [...] }`, `enhance.ts` (`requires` ⊆ `motion`, `webgl`). `scripts/themes.mjs` checks every slotted lab theme in `prebuild` and again when Vite loads the themes: files present, enhancement declared ⇔ module present, CSS within 40 KB, and isolation — every top-level selector (also inside `@media`/`@supports`/`@container`/`@layer`/`@starting-style`) starts with `:root[data-theme="<id>"]` (quoted), `@keyframes` names start with `<id>-`, `@property` names with `--<id>-`, `@font-face` families start with `<id>-`, nested rules may use `&` only as their first character (so `:is(&, body)` cannot widen the scope) and contain no at-rule other than the conditional ones, any other at-rule (`@import`, `@scope`, `@page`…) is refused, and `url()` must be relative to the theme folder (no scheme, no `/`, no `data:`). Nested rules without `&` are implicitly `& …` and inherit the parent's scope. An active lab theme must sit in a slot; archived ones are not checked.
- **What ships.** `astro.config.mjs` adds the Vite plugin `scripts/vite-themes.mjs`: `virtual:linkedia-themes/styles` imports the slotted labs' CSS after the baseline (one stylesheet), `…/slots` gives the three slots to the layout, and `…/enhancements` maps each slotted theme with a module to `() => import(enhance.ts)` — its own chunk, never preloaded. Archived themes stay in Git and never reach `dist`.
- **Markup.** Before the first experiment the output is the 1B baseline (only `data-theme="minimal-dark"`). Afterwards `<html>` carries `data-theme` (build-time default: current) and `data-theme-baseline|previous|current`; `<head>` gets the pre-paint script (`src/lib/theme-init.ts`); the footer gets `ThemeSwitcher.astro`: a `<fieldset>` "Tema visual" with three radios (Base, Anterior, Atual; Anterior disabled while `previous` is null), hidden until its script runs, plus an `aria-live` status line.
- **Choice.** `localStorage["linkedia:tema"]` holds a *slot* (`baseline`/`previous`/`current`), not a theme id, so "Atual" follows each new experiment. Reads and writes are wrapped in try/catch; anything else stored is ignored. The pre-paint script applies it before the body is parsed; its sha256 is in `firebase.json` `script-src` — changing the script means changing the hash (`tests/firebase.test.mjs` fails otherwise).
- **Runtime** (`src/lib/theme-runtime.ts`). A switch sets `data-theme`, aborts and cleans up the running enhancement, then imports the new theme's module only if the device meets every requirement (`motion`: no reduced-motion preference; `webgl`: a context can be created; unknown: unmet); otherwise the theme stays CSS-only. The module's default export gets `{ root, signal, fail }` and may return a cleanup; it must stop on `signal` abort. A failed import, a throw/rejection at start, `fail()`, or any uncaught error or unhandled rejection on the page while the enhancement runs (timers, frames, handlers; the site's own scripts are tiny, so it is blamed) → baseline (`data-theme-fallback="<id>"`, Base radio checked, announced); the stored choice is kept, so the next page tries again. A later choice supersedes a module still loading.
- **Tests.** `tests/themes.test.mjs` (manifest, packages, CSS isolation), `tests/theme-runtime.test.mjs` (controller, storage, pre-paint script), `tests/build.test.mjs` (bootstrap output unchanged; with the fixtures in `tests/fixtures/themes`: slots, one hashed inline script in `<head>`, lazy enhancement chunk, switcher JS ≤ 6 KB, archived theme not shipped, unscoped CSS fails the build), `e2e/themes.spec.mjs` (the e2e build uses the fixtures: keyboard switching and announcements, persistence across pages, pre-paint with the switcher script blocked, blocked storage, fallback on a failed, throwing or later-throwing module, `main` content identical across every switch and a fallback, reduced motion and no WebGL fetch no module — the current fixture requires both, so the other tests give pages a stand-in WebGL context —, no-JS default, axe + 320 px + visible switcher in each slot), `e2e/real-themes.spec.mjs` (1C-03, on the production build: each real slot × each page kind × 1100/320 px — axe, no horizontal scroll, layout shift, screenshots; no animation under reduced motion; no fallback without WebGL), `tests/theme-rollover.test.mjs`.
- **Adding a theme (rollover, 1C-03).** Commit the outgoing themes first, then `npm run theme:rollover -- --week 2026-W43 --title "Nome" [--summary "…"] [--dry-run]`: it refuses a malformed or nonexistent ISO week, a second theme for a week, a week not after the manifest's, and a previous theme with uncommitted changes; it moves the slots (`previous` ← old current, `current` ← `lab-2026-w43`, the theme leaving the slots → `archived` with `git_ref` = the last commit that touched its folder, so it can be rebuilt from Git), sets `week_id`, scaffolds `themes/<id>/` (`theme.css` with an empty scoped token block, README outline) unless the folder already exists, and runs the same validation as `prebuild`; if that fails, the manifest and its scaffold are restored. Then design the theme, write its README (concept, inspirations with URLs/dates, accessibility notes, fallback, reuse) and run `npm run check && npm test && npm run e2e`; look at the screenshots in `test-results/screenshots/<id>/` before committing.
- **Pitfall (1C-02).** The build's CSS minifier folds `animation` + `animation-timeline` in one rule into a single `animation` shorthand, which browsers drop (the timeline is reset-only in the shorthand). With scroll- or view-driven animations, write the animation as longhands (`animation-name`, `animation-timing-function`, …, `animation-timeline`).
- **Experiments so far.** `lab-2026-w42` "Broadsheet" (2026-W42): light newsprint, serif masthead, drop caps, CSS scroll-driven reading-progress rule; CSS only.

## Free creative brief
One new theme per ISO week maximum. The weekly concept may redesign the whole site or one element; experiments can be minimalist, vibrant, light, dark, procedural, 3D, shader-rich, WebGL or text-led. Search external inspiration, attribute sources and use original implementation. Avoid visual novelty that makes articles inaccessible.

## Quality gates
Keyboard, touch, screen readers, reduced motion, forced colors/high contrast where possible, small viewport, loading/fallback when 3D unsupported, Core Web Vitals budget, responsive reading contrast and no layout shift. A theme that fails gates must not replace baseline: keep new theme disabled until fixed.

## Optional dependencies
Start with Astro + CSS; add React and Motion only inside a theme that needs them. Bring Three.js, React Three Fiber or shaders ONLY when the specific week's concept needs them; lazy-load code and avoid adding them to the baseline bundle. Document alternative when WebGL is disabled.

## Reuse recipe
Provide instructions for extracting an experiment into another React/Astro project, minimal dependencies, design tokens, interfaces, lifecycle/canvas cleanup and licensing. Store screenshot references with the Git release/tag even if screenshot binary is not published.
